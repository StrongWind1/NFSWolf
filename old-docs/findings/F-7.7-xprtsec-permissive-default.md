# F-7.7: xprtsec Permissive Default (TLS/Plaintext Coexistence)

## Classification

- **Severity**: Medium
- **CVSS Vector**: Network / Low Complexity / No Auth Required
- **Affected Versions**: Linux knfsd with xprtsec support (kernel 6.x+)
- **RFC Reference**: RFC 9289 S1 (opt-in nature of NFS over TLS), RFC 9289 S6.1.1 (STRIPTLS attack)
- **Prerequisite**: Export configured with `xprtsec=tls` or `xprtsec=mtls`
- **Kernel Code**: `fs/nfsd/export.c:check_xprtsec_policy():1100-1118`, default at line 647

## Summary

When an administrator adds `xprtsec=tls` to an NFS export, the intent is to require TLS-encrypted transport. However, the kernel default for `ex_xprtsec_modes` is `NFSEXP_XPRTSEC_ALL`, which sets all three bits: `NONE|TLS|MTLS`. Adding `xprtsec=tls` enables the TLS bit but does not clear the `NONE` bit unless the administrator explicitly omits it. The result is that plaintext (non-TLS) connections continue to be accepted alongside TLS connections. An attacker simply connects without TLS and all NFS operations succeed -- no active STRIPTLS attack (F-3.4) is needed. This is the transport-layer equivalent of the RPCSEC_GSS flavor downgrade (F-1.7): the server offers both strong and weak options, and the attacker picks the weak one.

## Technical Detail

### Default xprtsec Configuration

In `fs/nfsd/export.c`, the default export options set all xprtsec modes:

```c
/* Line 647 */
exp->ex_xprtsec_modes = NFSEXP_XPRTSEC_ALL;
```

Where `NFSEXP_XPRTSEC_ALL` is defined as:

```c
#define NFSEXP_XPRTSEC_NONE  0x01
#define NFSEXP_XPRTSEC_TLS   0x02
#define NFSEXP_XPRTSEC_MTLS  0x04
#define NFSEXP_XPRTSEC_ALL   (NFSEXP_XPRTSEC_NONE | NFSEXP_XPRTSEC_TLS | NFSEXP_XPRTSEC_MTLS)
```

### The check_xprtsec_policy() Function

When an NFS operation arrives, the server calls `check_xprtsec_policy()`:

```c
/* Line 1100-1118 */
static int check_xprtsec_policy(struct svc_rqst *rqstp, struct svc_export *exp)
{
    if (exp->ex_xprtsec_modes & NFSEXP_XPRTSEC_NONE)
        if (!rqstp->rq_xprt->xpt_is_tls)
            return 0;  /* plaintext accepted */

    if (exp->ex_xprtsec_modes & NFSEXP_XPRTSEC_TLS)
        if (rqstp->rq_xprt->xpt_is_tls)
            return 0;  /* TLS accepted */

    if (exp->ex_xprtsec_modes & NFSEXP_XPRTSEC_MTLS)
        if (rqstp->rq_xprt->xpt_is_tls && rqstp->rq_xprt->xpt_peer_cert)
            return 0;  /* mTLS accepted */

    return -EACCES;
}
```

The function checks if ANY of the enabled modes match the connection's transport security. Because `NFSEXP_XPRTSEC_NONE` is enabled by default, a plaintext connection always passes the first check.

### The Administrator's Misunderstanding

An administrator writes:

```
/srv/share  client(rw,xprtsec=tls)
```

They expect this to require TLS. But the export parser treats `xprtsec=tls` as "enable the TLS bit" -- it does NOT disable the `NONE` bit. The effective configuration is `xprtsec=none:tls` (both plaintext and TLS accepted).

To actually require TLS, the administrator must explicitly exclude `none`:

```
/srv/share  client(rw,xprtsec=tls:mtls)
```

Or, depending on the export parser implementation, there may not be a syntax to disable `NONE` once it is in the default set. This depends on the kernel version and the export parser's handling of the `xprtsec` option.

### Comparison with F-1.7 (Flavor Downgrade)

| Dimension | F-1.7 (Flavor Downgrade) | F-7.7 (xprtsec Permissive Default) |
|-----------|-------------------------|-------------------------------------|
| Layer | Authentication (RPC auth_flavor) | Transport (TCP vs TLS) |
| Weak option | AUTH_SYS | Plaintext TCP |
| Strong option | RPCSEC_GSS (krb5/krb5i/krb5p) | TLS or mTLS |
| How the weak option persists | Admin adds `sec=sys` as fallback | `NONE` is in the default bitmask |
| Active attack needed | No (direct selection) | No (just don't use TLS) |
| MITM variant | Tamper MOUNT/SECINFO to remove krb5 | Not needed; plaintext is accepted |

Both findings share the same root cause: the server offers a menu of security options without enforcing a minimum. The attacker picks the weakest available option.

### RFC 9289 Context

RFC 9289 S1 explicitly acknowledges the opt-in nature of NFS over TLS:

> "RPC-with-TLS is an opt-in mechanism. Neither RPC client nor server implementations are required to support TLS."

RFC 9289 S6.1.1 describes the STRIPTLS attack: a MITM intercepts the TLS negotiation and forces the client to fall back to plaintext. However, this active attack is unnecessary when the server already accepts plaintext connections by default. The STRIPTLS attack (F-3.4) becomes relevant only when the server is correctly configured to reject plaintext.

## Impact

- **TLS requirement silently unenforced**: The administrator believes TLS is required, but plaintext connections succeed
- **Wire interception**: All AUTH_SYS identity attacks (F-1.1 through F-1.5) and credential replay (F-1.5) apply because the wire is plaintext
- **No active attack needed**: Unlike STRIPTLS (F-3.4), the attacker does not need to intercept or modify any traffic; they simply connect without TLS
- **False compliance**: Security audits may check for `xprtsec=tls` in the export configuration and incorrectly conclude that TLS is enforced

## Detection (nfswolf)

nfswolf detects this finding through transport probing:

1. **Connect without TLS**: The scanner connects to port 2049 with a plain TCP socket (no TLS handshake).
2. **Send GETATTR**: If the server accepts the plaintext GETATTR and returns `NFS3_OK`, TLS is not enforced.
3. **Cross-reference xprtsec**: If the export's auth_flavors or SECINFO suggest TLS awareness (presence of AUTH_TLS flavor 7 in the flavor list), the finding fires because the server advertises TLS but does not require it.

The check is passive and does not attempt a TLS connection (nfswolf does not implement a TLS client for NFS).

## Remediation

1. **Explicitly exclude plaintext** -- configure the export to accept only TLS and/or mTLS:
   ```
   /srv/share  client(rw,xprtsec=tls)
   ```
   Verify by checking the effective `ex_xprtsec_modes` in `/proc/net/rpc/nfsd.export` or by testing with a plaintext connection.

2. **Test the configuration** -- after setting `xprtsec=tls`, confirm that a plaintext `nfswolf scan` or `showmount -e` from a non-TLS client is rejected.

3. **Firewall port 2049** -- restrict access to clients that support TLS. This is defense-in-depth, not a substitute for correct xprtsec configuration.

4. **Combine with `sec=krb5p`** -- Kerberos privacy protection encrypts the RPC payload independently of the transport layer, providing encryption even if the TLS configuration is wrong.

5. **Monitor kernel version** -- the xprtsec option and its default behavior vary across kernel versions. Check the changelog for fixes to the default bitmask handling.
