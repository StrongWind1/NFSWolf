# F-5.10: pNFS Flex-File Layout Security Downgrade

## Classification

- **Severity**: Medium
- **CVSS Vector**: Network / Low Complexity / Low Auth Required
- **Affected Versions**: Linux knfsd with `pnfs` export option enabled (kernel 4.8+, `CONFIG_NFSD_FLEXFILELAYOUT`)
- **RFC Reference**: RFC 8435 (Flexible File Layout), RFC 5661 S12.9 (pNFS security)
- **Prerequisite**: Export has `pnfs` flag set (`NFSEXP_PNFS`, 0x20000); client has NFSv4.1 session
- **Kernel Code**: `fs/nfsd/flexfilelayout.c:nfsd4_ff_proc_layoutget():23-78`, `nfsd4_ff_proc_getdeviceinfo():81-126`, `fs/nfsd/nfs4layouts.c:nfsd_devid_seq:48`

## Summary

When pNFS flex-file layouts are enabled on a Linux knfsd export, the metadata server (MDS) responds to LAYOUTGET by handing the client the raw NFS file handle for the target file (line 64-65 of `flexfilelayout.c`) plus instructions to access the data server (DS) via NFSv3 with AUTH_SYS (line 95-96: `da->version = 3; da->minor_version = 0`). This downgrades the security model from NFSv4.1 (sessions, RPCSEC_GSS) to NFSv3 AUTH_SYS on the data path. The DS address comes from the server's own `rq_daddr` (line 101), and device IDs are assigned from a monotonically incrementing counter starting at 1 (`nfsd_devid_seq`, line 48 of `nfs4layouts.c`), making them trivially enumerable. Once a layout is granted, the `disable_recalls = true` flag (line 138) means the MDS cannot recall it or fence the client.

## Technical Detail

### LAYOUTGET Returns Raw File Handles

The `nfsd4_ff_proc_layoutget()` function (line 23-78) copies the server's internal file handle directly into the layout response:

```c
/* Line 64-65 */
fl->fh.size = fhp->fh_handle.fh_size;
memcpy(fl->fh.data, &fhp->fh_handle.fh_raw, fl->fh.size);
```

This handle is then used by the client to perform I/O directly against the data server via NFSv3. The handle is the same handle that `fh_verify()` would validate on the MDS -- it contains the fsid, fileid_type, and inode/generation. When the client contacts the DS with this handle, the DS performs its own `fh_verify()`, but now under NFSv3 AUTH_SYS rules instead of the NFSv4.1 session-authenticated MDS path.

### GETDEVICEINFO Leaks Server Address

The `nfsd4_ff_proc_getdeviceinfo()` function (line 81-126) returns the data server's network address. In Linux's "super-simple" flex-file implementation, the MDS and DS are the same server, so it returns its own address (`rqstp->rq_daddr`, line 101-102). The response includes:

- NFSv3 version (`da->version = 3`, line 95)
- TCP transport (`netid = "tcp"` or `"tcp6"`, lines 108-116)
- The server's IP and NFS port in universal address format (line 119-121)
- Maximum read/write sizes (`da->rsize = svc_max_payload(rqstp)`, line 98)

In enterprise pNFS deployments with separate MDS and DS infrastructure, the DS addresses expose the data server network topology to the client.

### Sequential Device IDs

Device IDs are allocated from a global sequential counter:

```c
/* nfs4layouts.c line 48 */
static u64 nfsd_devid_seq = 1;
/* ... line 89 */
map->idx = nfsd_devid_seq++;
```

An attacker can enumerate all pNFS-enabled exports by issuing GETDEVICEINFO for device IDs 1, 2, 3, ... until the server returns `NFS4ERR_NOENT`. Each valid ID reveals the DS address and transport configuration for a different export.

### Layouts Cannot Be Recalled

The flex-file layout driver explicitly disables recall:

```c
/* flexfilelayout.c line 138 */
.disable_recalls = true,
```

There is no `fence_client` callback. Once a layout (and its embedded file handle) is granted, the MDS has no mechanism to revoke it. If the client's access is subsequently revoked (export ACL change, Kerberos ticket expiry), the client can continue performing I/O via the DS using the cached NFSv3 handle indefinitely. The server's only recourse is restarting NFSD.

### Security Downgrade Chain

The full downgrade chain:

1. Client authenticates to MDS via NFSv4.1 with RPCSEC_GSS (e.g., `sec=krb5p`) -- encrypted, integrity-protected, Kerberos-authenticated
2. Client issues LAYOUTGET -- returns raw file handle + DS address
3. Client contacts DS via NFSv3 AUTH_SYS (`flexfilelayout.c` line 95: `da->version = 3`) -- no encryption, no integrity, attacker-controlled UID/GID
4. DS validates the handle but applies AUTH_SYS credential rules (no Kerberos enforcement on the data path)

The uid field for read layouts is deliberately set to `inode->i_uid + 1` (line 54), which is a crude attempt to prevent reads with the owner's UID. For write layouts, the actual `i_uid` is used (line 57). Both are AUTH_SYS credentials that the client controls.

## Impact

- **Security downgrade**: A pNFS-enabled export configured with `sec=krb5p` (encrypted, integrity-protected) has its data path silently downgraded to NFSv3 AUTH_SYS (plaintext, no integrity, forged credentials). All wire-level protections are lost on the I/O path.
- **Handle leakage**: The NFSv3 file handle embedded in the layout bypasses the MDS's access control for future operations. Combined with AUTH_SYS credential forging (F-1.1), the attacker can read/write any file for which they obtain a layout.
- **Irrevocable access**: `.disable_recalls = true` means access cannot be revoked once granted. Permission changes, export removal, and Kerberos ticket expiry have no effect on existing layout grants.
- **Topology disclosure**: GETDEVICEINFO reveals DS addresses and port numbers. Sequential device ID allocation enables enumeration of all pNFS exports.

## Detection (nfswolf)

Not currently implemented. Potential detection approach:

1. **Scanner**: After NFSv4.1 session establishment, issue LAYOUTGET on a file in each pNFS-enabled export. Check whether the layout response contains an NFSv3 file handle and DS address.
2. **Analyzer**: Flag exports with `NFSEXP_PNFS` (0x20000) and warn about the NFSv3 AUTH_SYS downgrade on the data path. Enumerate device IDs 1-N via GETDEVICEINFO to map DS topology.
3. **Fingerprinting**: The sequential device ID pattern (`1, 2, 3, ...`) confirms Linux knfsd flex-file layout.

## Remediation

- **Disable pNFS** on exports where security is more important than parallel I/O performance. Remove the `pnfs` export option.
- **Network segmentation**: If pNFS is required, restrict DS access to authorized client networks via firewall rules, since the NFS protocol provides no data-path authentication.
- **Monitor DS access**: Log NFSv3 connections to the DS port and alert on unexpected source IPs.
- pNFS block and SCSI layout types (not flex-file) do not have this NFSv3 downgrade issue because they use block-level access, not NFS file handles.
