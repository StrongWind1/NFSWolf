# F-3.6: UDP MOUNT Handle Theft via Source IP Spoofing

## Classification

- **Severity**: Critical
- **CVSS Vector**: Network / Low Complexity / No Auth Required
- **Affected Versions**: NFSv2, NFSv3
- **RFC Reference**: RFC 2623 §2.1, RFC 2623 §2.6, RFC 1057 §10
- **Prerequisite**: Same L2 segment as server (or ability to route reply to attacker); mountd listening on UDP; knowledge of allowed IP and export path

## Summary

When `rpc.mountd` serves over UDP, an attacker on the same Layer 2 segment can spoof the source IP of an allowed client in a UDP MOUNT MNT request. The server checks the source address from `recvfrom()`, matches it against the export ACL, and returns the file handle in the reply datagram. The attacker receives the reply (having added the spoofed IP to their NIC or via ARP interception). Once the handle is obtained, it is a bearer token (RFC 2623 §2.6) -- usable indefinitely from any IP over TCP without re-authentication.

This attack requires no TCP three-way handshake (UDP is connectionless), no knowledge of sequence numbers, and no ongoing IP spoof. The spoof is a one-shot operation to extract the handle.

## Technical Detail

### The Decoupled Architecture

Linux NFS has two daemons with separate access control:

```
                    +-----------+
                    | mountd    |  <-- checks IP ACL (export list)
                    | (port N)  |  <-- returns file handle on success
                    +-----------+
                         |
                    file handle
                         |
                         v
                    +-----------+
                    | nfsd      |  <-- NEVER re-checks export ACL
                    | (port 2049)|  <-- validates handle structure only
                    +-----------+
```

`mountd` is the ONLY gate. Once it issues a handle, `nfsd` on port 2049 serves requests for that handle from any source IP. The two daemons do not communicate -- there is no callback from nfsd to mountd to re-verify authorization.

### Where the IP Check Happens (Linux nfs-utils)

In `rpc.mountd` (utils/mountd/mountd.c), the MNT procedure:

```c
// mountd.c: mount_mnt_3_svc()
struct sockaddr *sap = nfs_getrpccaller(rqstp->rq_xprt);  // source IP from recvfrom()
// ...
exp = auth_authenticate("mount", sap, p);  // checks IP against /etc/exports
if (exp == NULL) {
    *error = MNT3ERR_ACCES;  // denied
    return NULL;
}
// ... on success: compose and return the file handle
```

`nfs_getrpccaller()` calls `svc_getcaller()` which returns the `struct sockaddr` from the transport layer. For UDP, this is the source address from the UDP datagram header -- trivially spoofable by the sender.

### Where the IP Check Does NOT Happen (Linux kernel nfsd)

In the kernel NFS daemon (fs/nfsd/nfsfh.c), every NFS RPC call goes through `fh_verify()` -> `nfsd_set_fh_dentry()` -> `rqst_exp_find()`. This function looks up the export by `(client_auth_domain, fsid)`. The auth_domain is derived from the source IP via the `ip_map` cache -- BUT the lookup is against ALL exports for that domain, not the specific restricted export. If the client has ANY export visible on the same filesystem (same fsid), the handle resolves successfully.

The kernel DOES NOT call back to mountd to ask "was this client authorized to receive this specific handle?"

### Attack Sequence

```
Preconditions:
  - /etc/exports: /srv/restricted  10.0.0.50(rw,insecure)
  - Attacker IP: 10.0.0.99 (NOT in ACL)
  - Attacker on same L2 as server
  - mountd listening on UDP (rpcinfo shows mountd/udp)

Step 1: Discover allowed IP and export path
  $ nfswolf scan <target>
  # Shows: /srv/restricted  10.0.0.50

Step 2: Add allowed IP to attacker's NIC
  $ ip addr add 10.0.0.50/24 dev eth0

Step 3: Send UDP MOUNT MNT from spoofed IP
  # Single UDP datagram: src=10.0.0.50:800 dst=<server>:<mountd-udp-port>
  # RPC CALL: prog=100005 ver=3 proc=1 args="/srv/restricted"
  # mountd checks recvfrom() addr -> matches ACL -> returns handle

Step 4: Receive reply (we have the IP on our NIC)
  # MNT3_OK + file handle (28 bytes)

Step 5: Remove spoofed IP, use handle over TCP from real IP
  $ ip addr del 10.0.0.50/24 dev eth0
  $ nfswolf shell <target> --handle <hex>
  # Works from any IP -- handle is a bearer token
```

### Requirements

| Requirement | Why | How to verify |
|-------------|-----|---------------|
| mountd UDP listener | UDP is connectionless, no handshake to complete | `rpcinfo -u <host> 100005 3` or scanner `--scan-udp` |
| Same Layer 2 segment | Must receive the UDP reply datagram | Attacker on same switch/VLAN/bridge as server |
| Knowledge of allowed IP | Must spoof a specific IP that passes the ACL | `showmount -e` / MOUNT EXPORT RPC (world-readable) |
| Knowledge of export path | Must specify the restricted path in MNT args | `showmount -e` / MOUNT EXPORT RPC |
| Privileged source port | Exports without `insecure` require src < 1024 | Requires root or CAP_NET_BIND_SERVICE |
| Allowed IP is not active on the network | If the real host is online, duplicate IP causes ARP conflict | Probe with ping/ARP first |

### Why This Defeats the "No Same-Filesystem Sibling" Defense

Administrators sometimes believe IP-restricted exports are safe because no wildcard exports exist on the same filesystem. This reasoning fails when the attacker can directly obtain the restricted export's handle via UDP MOUNT spoof -- no sibling export escape is needed.

## Exploitation

### With nfswolf (current)

```bash
# Obtain handle via external spoof (Python/scapy), then:
nfswolf shell <target> --handle <hex-from-spoof> --uid 0
```

### Key Property: One-Shot Spoof, Indefinite Access

The source IP only needs to be spoofed for the single UDP MOUNT MNT exchange. After the handle is extracted:
- Access continues over TCP from the attacker's real IP
- No ongoing spoof is required
- The handle survives server reboot, client reboot, export re-export (unless fsid changes)
- The handle survives the allowed client coming back online
- UMNT does not invalidate the handle (RFC 1094 Appendix A)

## Impact

- **Complete bypass** of IP-based export restrictions
- **Single-packet attack** -- one UDP datagram extracts the bearer token
- **Persistent access** -- handle never expires (see F-2.5)
- **Invisible** -- if attacker sends UMNT immediately after, no trace in MOUNT DUMP

## Detection

- Monitor for MOUNT MNT requests from IPs that don't match the allowed clients
- ARP monitoring (`arpwatch`) detects MAC/IP pairing changes
- Compare MOUNT DUMP entries against known clients
- Detect UDP MOUNT traffic from non-standard ports or unexpected source IPs
- Log `rpc.mountd` at debug level: `-d all` shows every MNT request with source IP

## Remediation

1. **Disable UDP on mountd** (`--no-udp` or `-u` flag):
   ```
   # /etc/default/nfs-kernel-server
   RPCMOUNTDOPTS="--manage-gids --no-udp"
   ```

2. **Disable UDP on nfsd** (remove UDP portlist entry):
   ```
   # /etc/nfs.conf
   [nfsd]
   udp=n
   ```

3. **Use Kerberos (RPCSEC_GSS)** -- makes IP-based access control irrelevant

4. **Network-level controls**: 802.1X, DHCP snooping, dynamic ARP inspection, port security

5. **Use NFSv4 only** -- eliminates the MOUNT protocol entirely

6. **Firewall mountd UDP port** even if the daemon listens on it:
   ```
   iptables -A INPUT -p udp --dport <mountd-port> -j DROP
   ```
